# Implementation sequence

Native firmware 0.4.0-beta.1 is a hardware beta operating standalone over Wi-Fi. Saved read-only channel profiles, positioned inline emotes and complete sender-name/login fallback are implemented. Every new owner supplies their own Wi-Fi and Public Twitch application settings. This document separates implemented stages from broader wearable requirements. Exact release qualification belongs to the attached summary and notes for the matching source/image; [verification](verification.md) preserves historical evidence, including source `54c1169c` whose successful API/CI/reproducibility checks did not override its failed active soak.

1. **Recoverable hardware baseline — delivered.** Full factory flash is independently verified and preserved; chip identity, original partitions and vendor provenance are recorded. Native touch uses the operational SDA4/SCL8 mapping. The SD card remains unmodified. Exact PCB revision and complete physical calibration remain separate.
2. **Pixels and touch — implemented.** Native AXS15231B full-frame QSPI output, portrait rendering and physical sampling operate. Long-message Back has historical physical evidence after the release/idle parser fix. Record all-corner and repeated-gesture checks, frame/input timing and longer stress for the relevant image. Native landscape is not implemented.
3. **Native chat UI — implemented.** Full-panel portrait chat uses the portable core, virtualized rows, floating settings/pause circles and an explicit Go live pill. Verified static emote occurrences replace their trigger text inline; unavailable or excess occurrences remain text. Display names retain 100 UTF-8 bytes with an exact ASCII login fallback. Host checks and current-image fixture/physical checks provide distinct evidence. Mounted readability remains open.
4. **Wi-Fi and login — implemented.** Local Node-backed USB setup, synchronized-time TLS, Public Device Code OAuth, saved credentials and token lifecycle run on device. The saved channel/read-only profile changes without recopying credentials through the UI caller. Future read-only consent requests only chat-read scope; broader existing grants remain unused and are not revoked by the profile setting. Normal operation has no desktop bridge. Qualify refresh/revocation and radio failure on the identified image.
5. **Live reading — implemented.** EventSub receives actual messages, with deduplication, deletion/clear handling, bounded queues and gap indication. Read-only profiles deny all action requests. Historical CDN download evidence does not by itself qualify changed inline layout. Do not claim server-history replay or busy-channel performance from initial reception.
6. **Moderation — implemented with historical API evidence.** Five actions on source `54c1169c` received acknowledgements and completed cleanup. Later read-only/profile changes have independent UI/core/worker denial tests. Bind every action to immutable IDs, confirm deliberately, report pending/success/error/unknown outcome and never replay offline. Preserve the baseline's source identity; review current regression coverage without representing those five actions as tests of the changed binary. Watched read-only channels are excluded from mutation tests.
7. **Wearable qualification.** Measure display readability outdoors and on camera, hotspot recovery, battery draw, temperature against skin, charging behavior and runtime. Confirm connector polarity, charger rating and cell protection against the actual board revision. Design a ventilated mount with strain relief and no exposed board or battery touching skin. No runtime estimate is justified until current is measured.

## Acceptance gates

These remain acceptance requirements unless a version-specific measurement or test is recorded. The v0.3.0 injected-scroll baseline was 15.503 fps. Controlled v0.3.2 scrolling with real chat/TLS measured about 15.34 fps with row-sprite caching off versus 15.39 fps on; that revision's cache default was off. The beta enables row sprites and backdrop culling; its performance, physical-input and active-soak gates require their own revision-specific evidence in [verification](verification.md).

- Sustained scrolling at least 30 displayed frames/s with frame-time p95 at or below 33 ms in the chosen display mode; finger-to-feedback p95 at or below 100 ms under TLS and burst chat. Measure on the physical panel, including transfer time.
- Paused viewport and selected target stay fixed during new arrivals, deletion events, layout changes and bounded history eviction. Any loss of retained history gets a visible marker. Return to live always requires an explicit action.
- A drag cannot activate moderation. A chat tap opens a sheet; a separate deliberate confirmation is required for an action. No hidden tap gesture directly bans.
- Core tests cover duplicates, bounded UTF-8 text, cross-channel identity, selection stability, pause/unread transitions, deletion/clear and eviction. Device replay includes 20 messages/s sustained for ten minutes and a 100 messages/s burst for five seconds while scrolling, with explicit overload accounting if the incoming queue fills.
- One-hour active soak plus repeated Wi-Fi loss/recovery: no watchdog resets, allocation drift, corrupt rows or silently replayed moderation requests. Record minimum free internal heap and largest DMA block, not just total PSRAM.
- A moderately busy channel remains readable at the chosen physical text size. A busy channel may outrun human reading; expose pause and unread count instead of shrinking the text or claiming all messages can be read.

## Decisions already made

Native firmware, standalone networking, EventSub chat, device login, bounded local scrollback, pause/live, identity-safe selection, saved read-only profiles, inline positioned emotes and complete sender attribution are implemented. Record dense-load/performance, physical, active-soak, CI and package evidence against its actual source and image. Earlier API and v0.3.x results remain historical. Battery, mounting and outdoor readability are separate wearable qualifications.

## Inputs and hardware work still needed

Each installation supplies its own Public Client ID, channel and local Wi-Fi settings. Remaining wearable inputs include preferred arm/mounting position, battery/strap dimensions and measured power/runtime requirements. Alternate orientation, final enclosure and battery qualification are future work, not login blockers.
